Atlassian Token Migration Principles

2026-05-22 18:22:45 WIB • Hadi K AR

Atlassian's token system uses a semantic, dot-separated naming hierarchy (category.subcategory.variant.state) that maps to CSS custom properties with a package prefix. Their three-step migration approach — set up theming, update components, replace raw values via codemod — provides a practical blueprint for Jakarta's --jkt- token strategy.

Background

Jakarta Design System (ds-jakarta) is being built from the ground up as a design token library. Before defining token naming conventions, categories, or CSS variable structure, it is worth studying the Atlassian Design System's token migration documentation as a primary reference — since the Jakarta CLAUDE.md explicitly cites it as the modelling basis.

This research surfaces the principles behind Atlassian's token naming, hierarchy, and migration tooling so that Jakarta can adopt the parts that are useful and consciously diverge where appropriate.

Scope

  • What design tokens are, per Atlassian's definition
  • The migration approach for developers and designers
  • Token naming conventions and the full category taxonomy (from @atlaskit/tokens@13.0.4)

Findings

1. Definition

Atlassian defines design tokens as "the single source of truth to name and store design decisions." They replace raw CSS values (e.g. #FF0000, 16px) with semantically named references that survive theme changes — enabling dark mode, high contrast, and future brand updates without touching component code.

2. Naming Convention

Tokens use dot-separated lowercase segments in code, converted to hyphen-separated CSS custom properties with the package prefix at output time.

category.subcategory.variant.state

color.background.danger → --ds-background-danger
color.background.danger.hovered → --ds-background-danger-hovered
color.text.accent.lime → --ds-text-accent-lime
space.200 → --ds-space-200
border.radius.100 → --ds-border-radius-100

The category segment is always the design property domain. State (hovered, pressed, selected, disabled) is always the last segment and optional — not every token has a state variant. Palette/raw values are never exported as public tokens; only semantic tokens are part of the API.

4. Token Function API

In TypeScript/JS, tokens are consumed via the token() function — not by hardcoding CSS variable names. This provides type checking, linting, and build-time transformation. 

import { token } from '@atlaskit/tokens';

// Returns CSS var reference at runtime, resolved at build time via Babel plugin
color: token('color.background.neutral');
// → var(--ds-background-neutral)

// Fallback arg (deprecated — avoid in new code)
background: token('color.background.danger', '#ffebeb');

The fallback argument is now discouraged — tokens are expected to always resolve via the theme.

5. Migration Approach (3 Steps)

  1. Set up theming — install the theme provider, apply it at the app root
  2. Update design system components — bring DS dependencies to the latest token-aware versions
  3. Replace raw values — run codemod CLI to auto-suggest token replacements, then review manually

Teams test the migration (especially dark mode) behind a Chrome extension toggle before public release. The codemod handles common patterns; edge cases require manual token selection.

Recommendation

Jakarta should adopt the Atlassian naming hierarchy (category.subcategory.variant.state) as the internal token model, replacing the ds- prefix with jkt- for CSS custom property output. Concretely:

  • Define tokens internally using dot-notation keys (even if TypeScript, not a token function): color.background.brand, space.200, border.radius.100
  • Emit CSS as --jkt-background-brand, --jkt-space-200, --jkt-border-radius-100 — strip the top-level category prefix for color tokens (matching Atlassian's pattern where color.* becomes --ds-* without the "color" segment)
  • Keep state variants (hovered, pressed, disabled) as the rightmost segment — never embed state in the middle of a name
  • Never expose raw palette values as public tokens — only semantic names
  • Expand token categories deliberately in this order: color → spacing → typography → border → elevation — matching Jakarta's planned roadmap
